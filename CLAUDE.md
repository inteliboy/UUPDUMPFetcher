## Approach
- Read existing files before writing. Don't re-read unless changed.
- Thorough in reasoning, concise in output.
- Skip files over 100KB unless required.
- No sycophantic openers or closing fluff.
- No emojis or em-dashes.
- Do not guess APIs, versions, flags, commit SHAs, or package names. Verify by reading code or docs before asserting.
- update claude.md itself with usefull information for future use

## Project overview
C#5/.NET Framework 4.8 WinForms tool, split across multiple `.cs` files compiled together by one `csc.exe` invocation in `build.cmd` (no external UI framework, no per-project references - see DeploymentTool's CLAUDE.md at `C:\Users\inteliboy\Desktop\DeploymentTool\CLAUDE.md` for the dark-WinForms conventions this project follows). Ships as a single `uupdump.exe` - only `libwim-15.dll`/`app.ico` live in `assets\` now (7z.exe/7z.dll/wimlib-imagex.exe were removed once nothing referenced them - see below); `libwim-15.dll` is embedded as a managed resource (`EmbeddedTools`) at compile time, extracted to `%TEMP%\uupdump_tools_<version>\` at runtime. `cabinet.dll` (used by `CabinetApi.cs`) needs no embedding - a real Windows system DLL, loaded off the System32 search path by name. `uupdump_gui.cs.orig_backup` is the pre-split monolithic source, kept as a reference/safety net - not part of the build.

Files: `Core.cs` (`NativeMethods`, `EmbeddedTools`, `Program`, `Paths`, `AppConfig`, `Logger`, `BuildState`) `Theme.cs` (`Theme`, `Ctrl` - palette + control factory) `Dialogs.cs` (`FlatProgressBar`, `ThemedMessageBox`) `Net.cs` (`Net` - HTTP/hash helpers) `WuClient.cs` (direct Windows Update SOAP client) `WimLibApi.cs` (direct libwim-15.dll P/Invoke binding) `CabinetApi.cs` (direct cabinet.dll P/Invoke binding) `Fetcher.cs` (`HtmlParser`, `BuildInfo`, `UupFile`, `Fetcher` - orchestrator) `Processor.cs` (`ToolHelper`, `Processor`, `LongIO`, `PsfPatcher` - MSU->WIM/PSF/ESD assembly) `MainForm.cs` (`MainForm`).

## wimlib: DLL-direct (no wimlib-imagex.exe)
`WimLibApi.cs` P/Invokes `libwim-15.dll` directly (the exe was only ever a thin CLI wrapper, used for one operation: `ToolHelper.WimlibCapture`, PSF-patched dir -> `.esd`). Every P/Invoke signature/flag/enum was taken from wimlib's real public header (`include/wimlib.h`) and `programs/imagex.c`, not guessed - `wimlib_tchar` is `wchar_t` (Unicode strings), calling convention is cdecl.
- `libwim-15.dll` isn't on the DLL search path (lives in `%TEMP%\uupdump_tools_<version>\`) - `WimLibApi.EnsureLoaded()` calls `LoadLibraryW` with the full path once; every subsequent bare `DllImport("libwim-15.dll")` then resolves against that already-loaded module.
- Capture flow: `wimlib_create_new_wim(LZMS)` -> `wimlib_set_output_pack_compression_type(LZMS)` -> `wimlib_register_progress_function` -> `wimlib_add_image` (flags `EXCLUDE_VERBOSE | WINCONFIG | VERBOSE | FILE_PATHS_UNNEEDED`, copied from `imagex.c`'s own `capture` defaults) -> `wimlib_write` (`WIMLIB_ALL_IMAGES | WIMLIB_WRITE_FLAG_SOLID`).
- Extraction: `ToolHelper.ExtractWim` calls `WimLibApi.ExtractWim` directly; `ExtractMsu` tries `WimLibApi.TryExtractAsWim` first and only falls back to the `CabinetApi`/classic-CAB path when wimlib reports `WIMLIB_ERR_NOT_A_WIM_FILE` (not an error - the signal to fall back).
- Some WIM images wrap their whole payload under one top-level "content" directory (`WimLibApi.FlattenSingleWrapperDir`) - only flattens when `outDir` has zero top-level files and exactly one top-level dir (an MSU extracted straight into `buildDir`, which already has sibling downloaded cabs, never qualifies - by design).
- **Long-path safety**: a real install.wim/WIM-format LCU extracts to tens of thousands of WinSxS-style files 100+ chars long, past MAX_PATH. Everything touching an extracted tree must go through `LongIO` (`EnumerateAll`/`DirExists`/`Move`/`DeleteDirectory`), never plain `System.IO`. Even `Path.GetDirectoryName` throws `PathTooLongException` on these in .NET 4.8 (calls `LegacyNormalizePath` internally) - don't assume any `System.IO.Path.*` method is exempt from path-length validation just because it looks like string manipulation; replaced with manual `LastIndexOf('\\')`/`Substring` where this bit.
- **Companion-directory lesson**: `wimExtract` (used by `ExtractWim`) and `PsfPatcher.Apply`'s own work dir were independently derived from different sibling files (`wimFile` vs `psfFile`) and silently diverged once either could nest under a "content" wrapper - caused a false-negative "CIX XML not found, skipping PSF patch" and a downstream `wimlib_add_image` failure (error 47, "Failed to open a file"). Fixed by deriving `wimExtract` from `Path.GetDirectoryName(wimFile)` to match. Any two independently-computed "companion directory" paths derived from different sibling files must use the same derivation, or one silently breaks when the other file's location changes.
- **Signature-mismatch lesson**: `wimlib_register_progress_function` returns `void`, not `int` like almost every other wimlib call - declaring it `int` compiles fine but silently reads garbage as a fake error code on the *next* call. A huge/nonsensical wimlib error number means check for a signature mismatch (return type, marshaling, arg count) before suspecting wimlib itself.
- **GC lesson**: a progress-callback delegate passed to native code needs `GC.KeepAlive()` covering every native call that might still invoke it - a bare local variable was eligible for GC mid-`wimlib_write` under real GUI allocation pressure (intermittent `NullReferenceException`, invisible in a low-GC-pressure console harness). Any future P/Invoke callback delegate here needs the same treatment.
- 23H2 ships standalone `.wim`/`.psf`/SSU cab (no `.msu` wrapper at all); 24H2/25H2/26H2/26H1 all ship the WIM-formatted "combined SSU+LCU checkpoint" `.msu` (~0.9-4.6 GB). Both paths, including PSF patching, are verified working end-to-end.

## Branch/build-number normalization
`26100.x`/`26200.x`/`26300.x` (24H2/25H2/26H2) and `22621.x`/`22631.x` (22H2/23H2) are separately-resolvable Microsoft update objects for the same underlying base OS build/payload.
- `BranchFromName` and a separate `baseNum`-normalization block in `Fetcher.Run` **both** encode "advertised build -> actual base build" knowledge - any future branch swap/add must update both, not just the one that determines the branch label. (Missed once during a 25H2->26H2 swap: `BranchFromName` was updated but the `baseNum` block wasn't, so a real download landed under the wrong folder/state key - fixed by renaming on-disk folders and hand-correcting state lines rather than re-downloading.)
- `26100`/`26200`/`26300` now all normalize to branch "Windows 11 26H2" and `baseNum` `26100.x`, so all three resolve to the same state key and aren't downloaded three times. `26100.x` searched directly still resolves as its own separate "Windows 11 24H2" branch - deliberate, since not every `26100.x` build has a `26200`/`26300` sibling (e.g. old RTM builds).
- Download folder is `downloads\<baseNum>\<arch>` (branch name dropped entirely - normalization already makes it redundant).
- NDP presence differs across sibling views of the same base build (e.g. the 26300.x view can omit the NDP cab while 26100.x/26200.x include it). `Fetcher.Run` gates automatic scans on NDP presence and, if missing, re-resolves other members of `NdpSiblingFamilies` (`26300/26200/26100`, `22631/22621`) via `NdpFallbackBuildNums`, substituting the first one that has it while keeping the original branch/baseNum for the download path. Manual/exact-build lookups bypass this gate.
- Test-automation gotcha: `RichTextBox`'s Win32 class name contains "EDIT" as a substring, so a driver matching controls with `-like "*EDIT*"` can grab the log panel instead of a real single-line edit box - filter with `-notlike "*RICH*"` too.

## State: builds.json (replaces downloaded_builds.txt)
`BuildState` (`Core.cs`) is `Dictionary<baseNum, Dictionary<arch, BuildRecord>>`, saved to `Paths.StateFile` via `JavaScriptSerializer` (`System.Web.Extensions.dll`, plain public fields work fine, no `{get;set;}` needed). `BuildRecord = {completedUtc, files:[{name,md5,sha256}]}` - same checksums already written as `.md5`/`.sha256` sidecar files; this is a second queryable copy, not a replacement. `Processor.ProcessBuild` returns `ProcessResult{Success,Files}` (was `bool`) so `Fetcher.Run` can save the file list without re-deriving it.

"Downloaded Builds" window (`MainForm.ShowState`) is a real per-row `Panel` grid (Name/MD5/SHA256 via `TableLayoutPanel`, `MakeGridCell`), collapsed by default behind a "▸ N file(s)" toggle.
- **Remove** drops just that arch key (or the whole baseNum entry if it was the last arch) and re-saves - doesn't touch files on disk. Since `Fetcher.Run`'s skip check is a state-dict lookup, removing the entry alone forces a full reprocess next scan (`Net.DownloadFile` still skips re-downloading any raw file whose checksum still matches).
- **Upload** (`Processor.UploadBuild`, split out of `ProcessBuild`'s upload/cleanup tail) re-triggers only the transfer on a background thread, always with `cleanup:false` regardless of `AppConfig.CleanupAfterUpload` - a manual re-upload must never silently delete the local build folder.
- When "Process update to ESD" is unchecked, the recorded `BuildRecord` has `completedUtc` but an empty `files` list - the viewer correctly shows "(no processed files recorded)" rather than fabricating checksums.

No native GUI automation tool exists in this environment (browser automation only) - WinForms changes are verified via a standalone harness: compile the real sources plus a throwaway `/main:` entry point, invoke the method under test via reflection, capture with `Control.DrawToBitmap` (client area only) or `GetWindowRect`+`Graphics.CopyFromScreen` (required for anything involving non-client chrome: title bar, window border, an open ComboBox dropdown that extends past the form) - then pixel-check the saved PNG, don't just eyeball it.

## Fetcher.TrimUnneededFiles - download only what Processor needs
Direct-from-Microsoft discovery doesn't pre-filter the way the uupdump.net scrape did - offers extra files (`AggregatedMetadata.cab`, `DesktopDeployment.cab`, old/duplicate `.msu`s) Processor never reads. Lives in its own `internal static` method (`Fetcher.TrimUnneededFiles`) specifically so standalone harnesses can unit-test it directly against captured file lists.
- 22621-family (22H2/23H2, no `.msu` wrapper): keep only `*.wim`, `*.psf`, `*SSU*`, `*NDP*`.
- Every other branch (default case, not a per-branch allow-list): keep only the single **largest** `.msu` by byte size (`UupFile.Size`, from `WuClient.FileEntry.Size` - degrades to "first in list" for the scrape-fallback path, which has no size field) plus the NDP cab - the checkpoint `.msu` already bundles WIM/PSF/SSU internally.
- **Edit-tool lesson**: an `Edit` whose `old_string` spans from one `if` block's leading comment through an unrelated following code region can silently delete that region instead of the intended one - an earlier version of this fix welded onto the wrong `if`, leaving one branch's trim only running for manual builds and another's not running at all, undetected until a real scan's log showed no "Trimmed to..." line. After any edit touching if/else control flow, re-read the surrounding braces to confirm the structure still says what it should - "it compiles" doesn't mean the logic is still right.

## Per-SKU servicing gaps (WuClient)
Windows editions can have genuinely different "latest" builds for the same branch - 23H2 Home/Pro's last cumulative update (`22631.6199`) is older than Enterprise/Education's (`22631.7517`), confirmed via Microsoft's own KB/lifecycle docs, not a ring/channel bug. `ComposeFetchUpdRequest`'s `sku` parameter (48 = Professional, matching uupdump.net's own default) was hardcoded everywhere.
- `DiscoverLatest` now probes `SkuProbeOrder = {48, 4}` (Professional, Enterprise) and keeps whichever resolves to the higher build (`CompareBuildStrings`).
- `ResolveUpdateOnlyFiles`'s own ring-probe loop needed the *same* sku loop independently - `GetExtendedUpdateInfo2` refuses to hand out CDN URLs for an Enterprise-only update when the request presents as sku=48, even though `SyncUpdates` resolves the update object fine either way. Deliberately not threaded through from discovery - manual exact-build lookups need the same independent probing, and any previously-silent `return null` path here now logs before failing.
- `DiscoverExact` (manual/`'thisonly'` build lookups) always uses sku=48 - verified irrelevant to exact-build resolution.
- Per-file KB descriptions are NOT recoverable from this protocol (tried and reverted - a real build's `SyncUpdates` response has only ~4 generic `<Title>` values total, not one per file). Filename pattern matching remains the only way this tool identifies what a given file is.

## WuClient protocol summary
Verified against live Microsoft responses and against uupdump.net's own open-source PHP backend (`git.uupdump.net/uup-dump`, a Gitea instance - WebFetch only returns an AI summary of it, use `curl -sL <url>/raw/branch/master/<path>` for real source).
1. GetCookie (SOAP, `fe3.delivery.mp.microsoft.com`) - cached ~20h in memory.
2. SyncUpdates (same endpoint) - filters to the leaf whose `ProductReleaseInstalled Name` matches `Client.OS.rs2.<arch>` exactly (multiple companion-product leaves can come back in one response). Response embeds child XML as HTML-escaped text inside `<Xml>` elements - parse the outer doc, then re-parse each unescaped fragment. Per-file metadata/title live in separate `<Update>` entries joined by the local numeric `<ID>`.
3. GetExtendedUpdateInfo2 (`fe3cr.delivery.mp.microsoft.com/secured`, no cookie needed) - real CDN URLs + SHA1, matched to names/SHA256 by SHA1.
4. Ring order auto-probed: RETAIL, WIF, WIS, RP, CANARY (`WuClient.RingProbeOrder`, shared by both `DiscoverInternal`'s SyncUpdates loop and `ResolveUpdateOnlyFiles`'s GetExtendedUpdateInfo2 loop - one fix covers both).
5. `'thisonly'` reaches builds over a year old directly from Microsoft - the "very old builds age off" limitation is real but narrower than assumed; the uupdump.net scrape fallback is kept deliberately as a failsafe, not removed.
6. **Missing-ring lesson**: CANARY was missing entirely until 2026-09 - the highest-numbered branch (28000.x, "26H1") ships Canary-Channel-only for a long stretch after it first appears, and RETAIL/WIF(Dev)/WIS(Beta)/RP never present as Canary to SyncUpdates, so `DiscoverLatest`/`ResolveUpdateOnlyFiles` silently found nothing for it even though the branch was correctly enabled/scanned. Fixed by adding `CANARY` to `RingProbeOrder` and a matching `ComposeDeviceAttributes` case (`fltBranch = "CanaryChannel"`) - confirmed against uup-dump/api's real `shared/requests.php` (`if($ring == 'CANARY') { $fltBranch = 'CanaryChannel'; $ring = 'WIF'; }`; the `$ring = 'WIF'` reassignment only matters for that PHP's own pre-17763 branch, unreachable here, so the C# port didn't need it). If a *newer* branch than 26H1 ever stops resolving the same way, check for another missing ring before suspecting the branch/baseNum logic.
7. **`DiscoverLatest` cannot see optional Preview Cumulative Updates - lesson + fix**: verified live 2026-09-07 that `WuClient.DiscoverLatest("28000.1", "amd64", ...)` kept returning 26H1's regular Patch Tuesday CU (28000.2704) even though a newer optional Preview CU (28000.2804, KB5120996) was already live - confirmed real via `WuClient.DiscoverExact("28000.2804", ...)`, which resolved it directly from Microsoft with no fallback needed. `DiscoverLatest`'s SyncUpdates "what's next for me" query only ever offers the mandatory/regular update track; a Preview build only gets surfaced when the request's own declared AppVer/OSVersion/MediaVersion already equals that exact Preview build number (confirmed: `DiscoverLatest` reseeded with `28000.2704` still returns `2704`, but reseeded with `28000.2804` correctly returns it) - there is no ordinary "give me whatever's newest" query shape that reaches it, and this is not something to try to fix by adjusting flags/rings/skus further. Fixed in `Fetcher.Run`'s automatic-scan loop (`Categories` loop): after `WuClient.DiscoverLatest` resolves an arch, uupdump.net's own `known.php?q=category:<slug>` listing (community/scan-tracked, already lists these Preview builds) is now queried unconditionally as a cross-check - not only when an arch was missed entirely, like before - and if it lists something newer, `WuClient.DiscoverExact` is used to resolve that exact build number directly from Microsoft. The uupdump.net fetch is wrapped in its own try/catch (a site outage must not abort scan categories that Microsoft already resolved fine on its own - it didn't need uupdump.net at all before this change).
8. **`ComposeFileGetRequest` needs `'thisonly'` too, not just SyncUpdates - lesson + fix**: initially assumed (wrongly) that resolving actual file URLs for 28000.2804/KB5120996 was a permanent get.php-fallback case, since `WuClient.ResolveUpdateOnlyFiles`'s `GetExtendedUpdateInfo2` call returned zero FileLocations for `DiscoverExact`'s UpdateID (`8f595bc2-...`) on every ring/sku, even though that same ID was clearly real (uupdump.net's own `get.php?id=8f595bc2-...` resolved it fine). Root cause found by reading uup-dump/api's real `get.php` (`git.uupdump.net/uup-dump/api`): it calls `uupApiReadFileinfo($updateId)` to reload the **exact ring/sku/branch/flags saved at discovery time** and replays that same context into `composeFileGetRequest`'s deviceAttributes - our C# `ComposeFileGetRequest` instead always built a fresh context with empty flags, so `MediaBranch` (only added when flags contains `'thisonly'` - see `ComposeDeviceAttributes`) was never set. Verified live 2026-09-07 by calling `GetExtendedUpdateInfo2` directly with the same UpdateID and only toggling flags: empty flags -> 0 `<FileLocation>` entries; `flags=['thisonly']` -> thousands, and `WuClient.ResolveUpdateOnlyFiles` then returns all 6 real files (correct sizes/SHA1, matching uupdump.net's own resolution exactly). Also verified live that adding `'thisonly'` to the *already-working* regular-CU case (28000.2704) resolves identically either way - so this is not conditional on how the update was discovered; `ComposeFileGetRequest` now always sends `flags=['thisonly']`. This means file-URL resolution for a build already identified by `DiscoverExact` no longer needs uupdump.net's get.php at all - that fallback is now only reached for a build genuinely old enough that Microsoft has aged it off live serving (WuClient's original, narrower use case for the scrape fallback), not for any live Preview build.
9. **Ring fallthrough can silently surface an unrelated branch/channel build - lesson + fix (2026-09-08)**: users reported off-family builds like `26340.9233` and `28020.2818` being auto-downloaded despite only 22621/22631/26100/26200/26300/28000 being enabled. Two independent causes, both real, found by tracing the two separate code paths that can introduce a build into `allBuilds`:
   - **uupdump.net cross-check (`Fetcher.Run`'s `Categories` loop)**: the "is uupdump.net's category listing newer" comparison (added for lesson 7 above) only compared build numbers numerically, never checked whether the scraped build's major actually belongs to the category's known family - uupdump.net's community scan tags some Canary/Dev-channel builds under the same `w11-26h2`/`w11-26h1` category slugs. Fixed with `Fetcher.CategoryBuildFamilies` (slug -> valid major-build-number prefixes, mirroring `BranchFromName`'s own mapping), filtering `scraped` immediately after parsing, before it's used for either the "newer" comparison or the arch-miss fallback loop.
   - **The actual root cause (this one alone reproduces `26340.9233` with zero uupdump.net involvement)**: `WuClient.DiscoverInternal`'s ring-probe loop (`RingProbeOrder`) returns the *first ring that answers with anything*, with no check that the answer's build major matches the branch being queried - `ParseSyncUpdates` only filters by architecture (`Client.OS.rs2.<arch>`), never by branch. When RETAIL has no delta to offer for a seed build (common and not itself a bug - a stable branch often has nothing queued at a given moment), the loop falls through to WIF/WIS/RP/CANARY (Insider channels), which answer with whatever *they* have - a completely different, much newer build - and that gets accepted and mislabeled with the queried branch's `branchDisplay` regardless. Verified live: querying 26H2's seed `26300.1` returned Dev-Channel build `26340.9233` off the WIF ring. Fixed by extracting the queried build's major from the `build` param (`"10.0.<major>.<minor>"`, so `bparts[2]`) inside `DiscoverInternal` and rejecting (continuing to the next ring, not returning) any ring answer whose `FoundBuild` major doesn't match - applies to both `DiscoverLatest` (seed-based) and `DiscoverExact` ('thisonly', where the major already matches by construction, so this is a no-op safety net there). Does not affect the CANARY-only-branch case (lesson 6) since CANARY's own answer for `28000.1` still has major `28000`.
   - Both fixes are necessary - each blocks the bug via a different path (uupdump.net-sourced vs. Microsoft-sourced-but-wrong-ring), and neither alone would have caught both reported build numbers.

## Assembly version auto-increment
`version.txt` holds `MAJOR.MINOR.BUILD.REVISION`; `build.cmd` bumps the revision only on every successful compile and generates `AssemblyVersion.generated.cs` (a build output, listed in `%SOURCES%`, not a tracked file) - no fixed `[assembly: AssemblyVersion]` in source anymore. Needed `setlocal enabledelayedexpansion` + `!VAR!` (not `%VAR%`) for the bump block specifically, since it reads a value set earlier in the same parenthesized block. Bump major/minor by hand-editing `version.txt`; auto-increment only ever touches the last number.

## 7z removed - CAB fallback is CabinetApi (cabinet.dll, no embedded binary, no subprocess)
Direct P/Invoke to the OS's own `cabinet.dll` (FDI API) - confirmed exporting `FDICreate`/`FDICopy`/`FDIDestroy`/`FDIIsCabinet` via `GetProcAddress`. No `LoadLibrary`-by-path dance needed (unlike `libwim-15.dll`) - resolves off System32 by name. Every struct/flag/constant verified against mingw-w64's real headers, Microsoft's FDI docs, and the Cabinet Format spec, not guessed. `DIAMONDAPI` is `__cdecl`.
- Safe to remove `7z.exe` entirely: every branch this tool currently handles resolves through `WimLibApi`, never classic CAB (23H2 has no `.msu` wrapper at all; 24H2/26H2/26H1 are all WIM-formatted checkpoints). `CabinetApi` is kept wired in anyway since it costs nothing (no embedded binary, no subprocess) in case a future Windows 10 patch level needs classic CAB.
- Same long-path issues as the WIM side, same fix (`LongIO` + manual path splitting, never `Path.Combine`/`GetFullPath`/`GetDirectoryName` on a path that might be deep).
- Verified byte-for-byte against real `7z.exe` offline (identical file count/paths/sizes/SHA256 on a real WinSxS-deep SSU cab) - not yet exercised against a real classic-CAB `.msu` live in the GUI, since none is currently needed.
- `SevenZipApi.cs` (an earlier direct-`7z.dll` COM-interop attempt) was deleted, fully superseded - it was blocked on `IInArchive.Open()` returning `E_POINTER` for WIM and failing at the extract callback for CAB; root cause never found despite verifying every GUID/vtable/PropVariant layout against real 7-Zip source. `CabinetApi`'s FDI approach avoids 7-Zip's COM interface entirely.

## Visual overhaul (Theme.cs/Ctrl, MainForm.cs)
Kept the `Theme`/`Ctrl` names (no DeploymentTool-style rename) but adopted its conventions: `FlatProgressBar`/`ThemedMessageBox` (`Dialogs.cs`) replace native progress bars/message boxes (native ones ignore theme entirely); `NativeMethods.EnableDarkScrollBar`/`SetPreferredAppMode`/`FlushMenuThemes` (`uxtheme.dll` ordinals 133/135/136 - the well-known undocumented table) theme native scrollbars dark; `Program.Main` calls `SetProcessDPIAware()` unconditionally.

**Recurring pattern across every fix below**: a native WinForms control under visual styles paints specific parts of itself (a `TabControl`'s header/frame, a `ComboBox`'s border/dropdown-button, a `TextBox`'s `FixedSingle` border) using fixed system colors that `BackColor`/`ForeColor` cannot reach. The fix is either `DrawMode.OwnerDrawFixed`+`DrawItem` (for content Windows will let you own) or a same-color sibling `Panel` overlay added *after* the control in z-order (for chrome Windows won't let you own at all) - a `Panel` added directly to a `TabControl`'s own `Controls` (as opposed to one of its `TabPage`s) never renders at all, so overlays must be Form-level (or same-parent) siblings, never children of the native control itself.

Current state:
- **Dark title bar / window border**: `NativeMethods.SetDarkTitleBar` (`DWMWA_USE_IMMERSIVE_DARK_MODE`, attribute `20` fallback `19`) + `SetBorderAndCaptionColor` (`DWMWA_BORDER_COLOR`=34, `DWMWA_CAPTION_COLOR`=35, Windows-11-only, `COLORREF` = `0x00BBGGRR`, not RGB byte order) - both called from `ApplyTheme` and from `ShowState` (a separate top-level `Form`/HWND needs its own call). `DrawToBitmap` cannot capture non-client chrome at all - use `GetWindowRect`+`CopyFromScreen`.
- **Tab strip** (`_tabs`): `OwnerDrawFixed`+`DrawTab` paints each tab's fill/text/2px accent underline using `tc.GetTabRect(e.Index)`, not `e.Bounds` (the two differ by only ~2px in practice - the normal owner-draw content margin, not a bug worth chasing further). `TabAppearance.FlatButtons` with `SizeMode.Fixed`/`ItemSize` measured from the longer label's real text (`TextRenderer.MeasureText`) gives equal-width tabs. Six sibling overlay panels cover everything the native strip still paints outside owner-draw: `_tabRowFill` (right of the last tab), `_tabFrameTop`/`_tabFrameBottom` (the page-frame border - `_tabFrameTop` starts 3px *above* the tab row's own bottom edge to hide a real native highlight line there, which as a side effect also hides the last ~2px of the accent underline; accepted trade-off), `_tabFrameLeft`/`_tabFrameRight` (4px wide, at the control's own left/right edges, spanning the full tab-row height), `_tabGroupTop` (FlatButtons' button-group outline, top edge only), `_tabInterGapFill` (the gap between the two tab buttons - only handles exactly 2 tabs, extend to loop over adjacent pairs if a third is ever added). All positioned from `_tabs.GetTabRect(...)`, recomputed on `_tabs.Resize`, and re-colored to `Theme.Bg` on every `ApplyTheme()` call.
- **Architecture ComboBox** (`_cmbArch`): `OwnerDrawFixed`+`DrawComboItem` themes the closed box's text and every open dropdown-list row (Windows always renders the list natively otherwise) - but never reaches the surrounding chrome. `FlatStyle.Flat`'s own border (~3px, left/top/bottom) and its entire dropdown-button face (~20px on the right, arrow included) render a fixed `240,240,240` regardless of theme. Four overlay panels cover this: `_archBorderLeft/Top/Bottom` (`Theme.Border`) and `_archButtonFace` (`Theme.EntryBg`, with a hand-drawn triangle arrow via its own `Paint` handler, since it fully covers the native one) - sized from `_cmbArch.PreferredHeight` (its assigned `.Height` is silently overridden by Windows) and empirically-measured 3px/20px thicknesses. Dark mode only, toggled via `ApplyTheme` - light mode's `FlatStyle.Standard` already renders correctly natively.
- **TextBox border** (`Ctrl.MakeEntry()` fields): `BorderStyle.FixedSingle`'s border color isn't settable and always renders `240,240,240`. `Ctrl.Bordered(TextBox)` wraps it in a Panel: dark mode sets `BorderStyle.None` plus a 1px `Theme.Border`-colored `Padding` on the wrapper; light mode leaves the native `Fixed3D` border untouched (a zero-padding pass-through wrapper, so light mode is unaffected). Sized from `tb.PreferredHeight`, not the caller's `.Height` - a single-line TextBox silently clamps to its font's natural line height regardless of any explicitly-assigned Height, so sizing off the requested Height left an asymmetric leftover-space border band. `RestyleEntries` (runtime theme toggle) calls `Ctrl.RestyleBordered(Panel)` for any TextBox whose parent is this kind of single-child wrapper.
- **Settings-tab row buttons of mismatched size**: `AddSettingRow` (shared by every Settings-tab field) used `Dock.Fill` on each row's container Panel, stretching it to the `TableLayoutPanel` row's full AutoSize height - and a two-line label (Upload destination) makes its row taller than a single-line one (Download destination) above it, so their "..." browse buttons (`Dock.Right` inside) ended up different heights despite both row Panels declaring the same explicit `Height`. Fixed with `Anchor = Top|Left|Right` instead of `Dock.Fill` - stretches width the same way but leaves the row's own explicit Height alone.
- **"Downloaded Builds" list**: real `TableLayoutPanel` grid (Name/MD5/SHA256, column widths sized from real `MeasureString` metrics) instead of one overflowing monospace line; cells are read-only borderless `TextBox`es, not `Label`s (a `Label` can't be selected/copied); dark scrollbar via `EnableDarkScrollBar`; collapsed by default behind a "▸ N file(s)" toggle.
- **Known, disclosed, not-yet-fixed gap**: `ApplyTheme()` never re-colors `Button`s (`NormalButton`/`AccentButton`/`DangerButton`) or the `topBar`/`statusBar` Panels on a runtime light/dark toggle - only correct at startup, since the constructor picks the real OS theme before building them.

**Lessons that generalize beyond this specific UI**:
- A coarse/narrow pixel-check (a handful of coordinates, or a fixed-step grid) walks right past thin borders the same way eyeballing does - scan every row/column of a real screenshot, or fall back to a raw unfiltered per-pixel dump of the suspect region, before declaring a visual bug fixed. A density/span heuristic scan can also produce a false "clean" result when two unrelated defects share a row/column and dilute each other's density below threshold.
- Cross-referencing a reflection-queried value against a screenshot through two coordinate transforms (client->screen via `ClientToScreen`, then screen->image via the window's own `GetWindowRect` origin) is easy to get subtly wrong. When a same-process API comparison looks suspicious, log the two raw values from the exact call site itself before trusting a cross-referenced screenshot measurement - this is what caused a false "`e.Bounds` doesn't match `GetTabRect`" lead above (the real difference was ~2px, not the ~12px actually seen on screen, which came from an unrelated overlay-panel sizing bug).
- `TextBox.Height` and `ComboBox.Height` are not reliable once assigned - both silently clamp to their font's natural preferred height regardless of what's set. Use `.PreferredHeight` when sizing anything around them.
- No native GUI automation tool exists in this environment - verify WinForms visual changes via a standalone harness (real sources + throwaway `/main:` entry point) using reflection plus `DrawToBitmap`/`GetWindowRect`+`CopyFromScreen`, never by trusting "it compiles."
