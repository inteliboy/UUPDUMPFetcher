## Approach
- Read existing files before writing. Don't re-read unless changed.
- Thorough in reasoning, concise in output.
- Skip files over 100KB unless required.
- No sycophantic openers or closing fluff.
- No emojis or em-dashes.
- Do not guess APIs, versions, flags, commit SHAs, or package names. Verify by reading code or docs before asserting.
- update claude.md itself with usefull information for future use

## Project overview
C#5/.NET Framework 4.8 WinForms tool, split across multiple `.cs` files compiled together by one `csc.exe` invocation in `build.cmd` (no external UI framework, no per-project references - see DeploymentTool's CLAUDE.md at `C:\Users\inteliboy\Desktop\DeploymentTool\CLAUDE.md` for the dark-WinForms conventions this project follows). Ships as a single `uupdump.exe` - only `libwim-15.dll`/`app.ico` live in `assets\` now (7z.exe/7z.dll/wimlib-imagex.exe were removed once nothing referenced them - see "wimlib"/"cabinet.dll" sections below); `libwim-15.dll` is embedded as a managed resource (`EmbeddedTools`) at compile time, extracted to `%TEMP%\uupdump_tools_<version>\` at runtime. `cabinet.dll` (used by `CabinetApi.cs`) needs no embedding at all - it's a real Windows system DLL, loaded off the System32 search path by name. `uupdump_gui.cs.orig_backup` is the pre-split monolithic source, kept as a reference/safety net - not part of the build.

Files: `Core.cs` (`NativeMethods`, `EmbeddedTools`, `Program`, `Paths`, `AppConfig`, `Logger`, `BuildState`) `Theme.cs` (`Theme`, `Ctrl` - palette + control factory) `Dialogs.cs` (`FlatProgressBar`, `ThemedMessageBox`) `Net.cs` (`Net` - HTTP/hash helpers, unrelated to WU protocol) `WuClient.cs` (direct Windows Update SOAP client - see below) `WimLibApi.cs` (direct libwim-15.dll P/Invoke binding - see below) `CabinetApi.cs` (direct cabinet.dll P/Invoke binding - see below) `Fetcher.cs` (`HtmlParser`, `BuildInfo`, `UupFile`, `Fetcher` - orchestrator) `Processor.cs` (`ToolHelper`, `Processor`, `LongIO`, `PsfPatcher` - MSU->WIM/PSF/ESD assembly) `MainForm.cs` (`MainForm`).

## wimlib: DLL-direct, no wimlib-imagex.exe
`wimlib-imagex.exe` is no longer shipped or embedded - it was only ever a thin CLI wrapper over `libwim-15.dll`, and this tool only ever used it for one operation (`ToolHelper.WimlibCapture`, called once from `Processor.ProcessBuild` to turn the PSF-patched work directory into the final `.esd`). `WimLibApi.cs` P/Invokes `libwim-15.dll` directly for that operation instead.
- Verified empirically before writing any binding code: `GetProcAddress` against the actual shipped `assets\libwim-15.dll` confirmed every needed symbol is exported (same as any native program linking against wimlib would see) - this DLL reports itself as wimlib 1.14.5. Every P/Invoke signature, flag value, and enum value in `WimLibApi.cs` was taken from wimlib's real public header (`include/wimlib.h`) and CLI source (`programs/imagex.c`), fetched fresh from `github.com/ebiggers/wimlib` and read directly - not guessed.
- `wimlib_tchar` is `wchar_t` on Windows -> every string P/Invoke parameter is Unicode. Calling convention is cdecl (`WIMLIBAPI` carries no stdcall decoration - `__declspec(dllexport)` only).
- **`libwim-15.dll` isn't on the DLL search path** (it lives in `%TEMP%\uupdump_tools_<version>\`, extracted at runtime) - `WimLibApi.EnsureLoaded()` calls `LoadLibraryW` with the full path once; the Win32 loader then resolves every subsequent bare `DllImport("libwim-15.dll")` call against that already-loaded module by name. `Paths.WimLibDll` (replaces the old `Paths.WimLib` exe path) points at it.
- The capture flow: `wimlib_create_new_wim(LZMS)` -> `wimlib_set_output_pack_compression_type(LZMS)` (the "--solid" part) -> `wimlib_register_progress_function` (real byte-level progress via the `WIMLIB_PROGRESS_MSG_WRITE_STREAMS` struct - a genuine upgrade over the old stdout-text-scraping, since the CLI-based version had no numeric progress at all for this step) -> `wimlib_add_image` with add-flags copied exactly from `imagex.c`'s own `capture` command defaults (`EXCLUDE_VERBOSE | WINCONFIG | VERBOSE | FILE_PATHS_UNNEEDED` - `WINCONFIG` matters, it's wimlib's standard Windows capture exclusion list) -> `wimlib_write` with `WIMLIB_ALL_IMAGES` + `WIMLIB_WRITE_FLAG_SOLID`.
- **Signature bug caught during testing, worth remembering**: `wimlib_register_progress_function` returns `void`, not `int`, unlike almost every other wimlib call. Declaring it as returning `int` didn't fail to compile or immediately crash - it silently read garbage off the stack/register as a fake error code on the *next* call, which is exactly the kind of P/Invoke mismatch that produces a nonsensical giant negative "error code" rather than a clean failure. If any future wimlib binding here throws with a huge or nonsensical error number, suspect a signature mismatch (wrong return type, wrong marshaling, wrong arg count) before suspecting wimlib itself - re-check the real header rather than guessing.
- Tested live end-to-end twice: once via a standalone driver capturing a real ~117 MB PSF-patched work directory to a 65.7 MB `.esd` (verified readable afterward via `wimlib_open_wim`/`wimlib_get_wim_info`, reporting `image_count=1`), and once through the real `uupdump.exe` GUI doing a full fresh download+extract+patch+capture of the 23H2 build used elsewhere in this doc - produced a genuine 924 MB checksummed `.esd`, slightly faster than the old exe-based path, with visible incremental progress logging (`Creating ESD: 10%/20%/.../100%`) where before there was only silence between "Creating ESD..." and "Generating MD5/SHA256 checksums...". Confirmed via `Get-Process` that no `wimlib-imagex` process ever spawns now.
- **Extraction converted too, later session**: `ToolHelper.ExtractWim` now calls `WimLibApi.ExtractWim` (wimlib-direct, no subprocess) instead of shelling out to `7z.exe`. `ToolHelper.ExtractMsu` tries `WimLibApi.TryExtractAsWim` first (a modern WIM-formatted `.msu` - see the "combined SSU+LCU checkpoint" note below) and only falls back to the `7z.exe` subprocess for genuinely CAB-formatted `.msu`s (`WIMLIB_ERR_NOT_A_WIM_FILE` from wimlib is the signal to fall back, not an error). `7z.exe` is now CAB-only.
- Some WIM images extract with their whole payload under one real top-level directory (`WimLibApi.FlattenSingleWrapperDir`, named "content" in every case seen so far) - a real folder baked into the image's own file tree (matching `<NAME>content</NAME>` in the WIM's own XML metadata), not just extraction metadata. Only flattens when outDir has zero top-level files and exactly one top-level dir - an MSU extracted straight into `buildDir` (which already has sibling downloaded cabs sitting there) never qualifies, by design, so its "content" wrapper is expected to persist; only a clean target directory (like `wimExtract`, extracted from an already-located standalone `.wim`) can actually flatten.
- **Everything touching a wimlib-extracted tree must be long-path safe (`LongIO`, not plain `System.IO`)** - a real install.wim/WIM-format LCU extracts to tens of thousands of files under WinSxS-style directory names 100+ chars long, which blows past MAX_PATH (260) the moment they're combined with any nontrivial `outDir` depth. Three separate spots in `Processor.cs`/`WimLibApi.cs` hit this and got fixed the same way (rewritten with `LongIO.EnumerateAll`/`DirExists`/`Move`/`DeleteDirectory`, never `Directory.GetFiles`/`GetDirectories`/`Move`/`Delete` on a path that might be this deep): `WimLibApi.FlattenSingleWrapperDir`, `Processor.FindFirst` (was `Directory.GetFiles(dir, pattern, SearchOption.TopDirectoryOnly)` - not recursive, so it also couldn't be used across the "content" wrapper, see next point), and the hotpatch-detection scan + "Cleaning up WIM extract..." step in `Processor.ProcessBuild` (both used to call `Directory.GetFiles(..., SearchOption.AllDirectories)`/`Directory.Delete(path, true)` directly on the deep extracted tree). If a future PathTooLongException surfaces anywhere near WIM extraction, check for a stray plain-`System.IO` call on the extracted tree before assuming it's something new.
- **`FindFirst` had to become recursive, which then exposed a path-consistency bug worth remembering**: originally `Processor.FindFirst(buildDir, pattern)` only searched `buildDir`'s top level, which silently returned nothing once wimFile/psfFile could be nested under a "content" wrapper (a "combined SSU+LCU checkpoint" MSU's WIM contents extract straight into `buildDir` and never flatten, per the point above) - this surfaced as `Processor error: Required files missing: WIM, PSF, SSU CAB` even though extraction had genuinely succeeded. Fixed by rewriting `FindFirst` as a recursive `LongIO`-based search (simple `*`-only glob converted to an anchored, case-insensitive `Regex`). That fix then exposed a SECOND, more subtle bug: `wimExtract` was computed as `Path.Combine(buildDir, Path.GetFileNameWithoutExtension(wimFile))` - i.e. always relative to the fixed outer `buildDir` - while `PsfPatcher.Apply` independently computes its own work directory as a sibling of wherever `psfFile` actually is (`Path.Combine(Path.GetDirectoryName(psfFile), psfStem)`). These two coincide only when wimFile/psfFile sit directly in `buildDir` (always true before `FindFirst` became recursive) - once they can be nested under "content", the two computed paths diverge: `wimExtract` (used by `ToolHelper.ExtractWim` to actually populate the directory) pointed one level higher than `PsfPatcher.Apply`'s workDir, so PSF patching saw an empty/nonexistent directory, silently reported "CIX XML not found - skipping PSF patch" (a false negative - the CIX XML was really there, just under the other path), and the subsequent `wimlib_add_image` capture call failed with **wimlib error 47 ("Failed to open a file")** trying to scan that empty/nonexistent directory. Fixed by computing `wimExtract` from `Path.GetDirectoryName(wimFile)` instead of the fixed `buildDir`, which realigns it with `PsfPatcher.Apply`'s own computation exactly. **Lesson**: any two independently-computed "companion directory" paths derived from different sibling files (here, wimFile vs. psfFile) must be derived the same way, or a location assumption baked into one silently breaks when the other file's actual location changes.
- **"Combined SSU+LCU checkpoint" MSU builds (25H2 build 26100.9278 amd64+arm64, ~900 MB WIM payload each) are now verified working end-to-end** after the three fixes above - real PSF patch applied (91,278 files for the arm64 build), real ~2.3-2.5 GB checksummed `.esd` produced, `Build marked complete`. This corrects the earlier assumption in this doc that 24H2+/25H2 checkpoint builds were an untested/complex edge case - they aren't anymore. 23H2 (~1 GB total, no checkpoint) is still the cheaper build for a quick smoke test, but 24H2+/25H2 checkpoint builds are no longer expected to fail.
- **Branch category note**: the "Windows 11 25H2" `Fetcher.Categories` entry (seed `26200.1`, which is where build 26100.9278 above came from) was later replaced outright with "Windows 11 26H2" (seed `26300.1`) - a real branch swap, not a rename, done once 26H2 became the current branch to track. Historical notes in this doc that say "25H2" describe what was true when that testing happened; the tool itself no longer has a 25H2 category/checkbox.
- **Real bug from that swap, worth remembering for the next branch swap**: `Fetcher.Run`'s `baseNum` normalization block (separate from `BranchFromName`) maps an *advertised* enablement-package build number down to the *actual* underlying base OS build Microsoft serves files under - `26200.x` (25H2's advertised number) mapped to base `26100.x` the same base OS build 24H2 uses. This block was NOT updated when 25H2's category was swapped for 26H2 (advertised `26300.x`, same `26100` base) - so a real live test genuinely fetched and stored a whole build (~2.4 GB each arch, PSF-patched, checksummed) under the *wrong* folder name (`Windows_11_26H2\26300.9278\...` instead of `\26100.9278\...`), and the `downloaded_builds.txt` state key was wrong too. Fixed by changing the `if (buildNum.StartsWith("26200"))` check to `"26300"` (matching `BranchFromName`'s own equivalent check, which *was* updated correctly during the swap - the bug was only in this second, separately-maintained normalization block). **Lesson: `BranchFromName` and the `baseNum` block in `Fetcher.Run` encode the same "advertised → actual base build" knowledge in two separate places - any future branch swap/add must update both, not just the one that determines the branch label.** The already-downloaded data was salvaged by renaming the on-disk folders (both the outer `<branch>\<baseNum>\<arch>` and the inner `Processor`-created `<buildVer>\<arch>` output folder) and correcting the two `downloaded_builds.txt` lines, rather than re-downloading - verified afterward with a real run that correctly recognized the renamed build as already-complete and skipped it.
- **Manual build search now folds all three enablement-package "views" of the same content into one consistent branch/folder.** Verified live and directly against Microsoft (`WuClient.DiscoverExact`, real TLS-enabled standalone harness, not guessed): `26100.9278`, `26200.9278` and `26300.9278` are three genuinely separate, independently-resolvable update objects - distinct UpdateIDs, distinct titles ("Windows 11, version 24H2"/"25H2"/"26H2" respectively) - built on the exact same base OS build and (as far as this tool's filter chain can tell) the same actual LCU/SSU/PSF payload. Manually searching any of them used to land in a different (or, for `26200.x`, a dead/no-longer-existing "25H2") branch folder, causing the same content to download three separate times depending on which number a user happened to type. Fixed by adding `26200.x` to both `BranchFromName` (→ `"Windows 11 26H2"`, folding the retired 25H2 view into the branch this tool actually tracks now) and the `baseNum` block (→ normalizes to `26100.x`, same as `26300.x` already did) - `26200.9278` and `26300.9278` now both resolve to state key `Windows 11 26H2_26100.9278_<arch>` and are correctly recognized as the same already-downloaded build. **Deliberately NOT unified further**: `26100.x` searched directly still resolves as `"Windows 11 24H2"` (unchanged) and lands in its own separate branch folder - a real, disclosed asymmetry, not an oversight. Blindly folding every `26100.x` build into "26H2" would mis-file genuinely build-specific 24H2-only lookups (e.g. the 24H2 RTM build `26100.1742` from before 25H2/26H2 enablement packages existed, which has no `26200`/`26300` equivalent at all) into the wrong branch. Verified live via the GUI's manual-build field for both cases (`26200.9278` → correctly skipped as already-downloaded; `26100.9278` → correctly started a fresh, separate download, which was stopped/cleaned up after confirming the log line rather than let it complete).
- **Test-automation gotcha hit again while verifying this**: `RichTextBox`'s real Win32 class name (`RichEdit20W`/similar) contains "EDIT" as a substring, so a driver script matching child controls with `-like "*EDIT*"` can silently grab the log panel instead of a real single-line edit box when enumeration order puts the RichTextBox first - the script "succeeded" (no error) but set the build-number text into the log panel instead, and `OnStart()` then correctly saw an empty build field and ran the LATEST-scan path instead of a manual search, which happened to produce plausible-looking-but-wrong log output. Caught by reading the actual `_tbBuild`/log-panel handles back and noticing they were identical. Fix: match `-like "*EDIT*" -and -notlike "*RICH*"` for a genuine single-line edit box.

## Download folder flattened to baseNum+arch (branch dropped); state is now builds.json
`Fetcher.Run`'s `targetDir` (Fetcher.cs, was `Path.Combine(Paths.DownloadDir, b.Branch.Replace(" ","_"), baseNum, b.Arch)`) dropped the branch component - now `downloads\<baseNum>\<arch>`. Per the "Branch category note"/"Real bug" sections below, `26100.x`/`26200.x`/`26300.x` (24H2/25H2/26H2) and `22621.x`/`22631.x` (22H2/23H2) already normalize to the same `baseNum` before this point - the same underlying Microsoft-served payload was still getting a separate folder per branch label even though it's the identical build, which is what this flattening fixes. `Processor.ProcessBuild`'s own `arch`/`buildVer` derivation (`Path.GetFileName(buildDir)` / `Path.GetFileName(Path.GetDirectoryName(buildDir))`) needed no change - it only ever looked at `buildDir`'s own last two path segments, which are still `<baseNum>\<arch>` regardless of how many parent directories precede them.

`downloaded_builds.txt` (one flat `branch_baseNum_arch` line per completed build) is replaced outright by `builds.json` (`Paths.StateFile`, same location, `BuildState.Load`/`Save` in Core.cs) - not a flat list any more but nested `Dictionary<string, Dictionary<string, BuildRecord>>`: outer key is `baseNum`, inner key is `arch`, so 24H2/25H2/26H2 (or 22H2/23H2) views of the same build share one outer entry, and each arch fills in its own sibling key independently as it completes (verified live: adding an `arm64` entry after `amd64` already exists leaves the `amd64` entry untouched - see the `BuildStateTest` harness pattern below). Deliberately NOT `"<baseNum>_<arch>"` string keys - arch is already the nesting level, so it never needs to be duplicated into a string. `BuildRecord` = `{ completedUtc, files: [BuildFileRecord] }`; `BuildFileRecord` = `{ name, md5, sha256 }` - the same md5/sha256 that were already being written as `.md5`/`.sha256` sidecar files next to each output file in `Processor.ProcessBuild` (kept, per explicit user instruction - builds.json is a second queryable copy of those checksums, not a replacement for the sidecar files). `Processor.ProcessBuild` changed its return type from `bool` to a new `ProcessResult { Success, Files }` (Files only populated on success) so `Fetcher.Run` can capture that list without re-deriving it. `Success = false` still means the same cooperative hotpatch-skip as the old `false` did - unaffected by this change. Serialization uses `System.Web.Script.Serialization.JavaScriptSerializer` (confirmed present in the default `csc.rsp` reference set - `/r:System.Web.Extensions.dll` - via `cat` on the real file on this machine, not guessed) with plain public fields on both record classes (verified live via a standalone harness that JavaScriptSerializer serializes/deserializes public fields fine, same as properties - no need for `{ get; set; }` here, consistent with every other POCO in this codebase like `BuildInfo`/`UupFile`/`FileEntry`). `MainForm.ShowState`/`ClearState` (previously read/wrote `Paths.StateFile` as raw text lines directly, bypassing `BuildState` entirely) now go through `BuildState.Load`/`Save`. No existing on-disk downloads or `downloaded_builds.txt` existed at the time of this change (verified by listing the configured download dir before editing), so no migration was needed this time - if that's ever not the case for a future change, migrate rather than losing track of completed builds (see the 25H2->26H2 rename precedent below, which renamed folders and fixed state lines by hand instead of re-downloading).

## "Downloaded Builds" window is a real table now (Remove / Upload per row)
`MainForm.ShowState` (the "View downloaded builds" button) no longer dumps `builds.json` as text in a RichTextBox - it builds one themed `Panel` row per `(buildNum, arch)` entry inside a `FlowLayoutPanel` (`TopDown`, `AutoScroll`), each row showing the build/arch header, `completedUtc`, and every recorded file's name with **both** `md5` and `sha256` (the earlier version only showed sha256 - fixed per explicit ask). Built from scratch with `Theme`/`Ctrl` rather than a `DataGridView`, matching this project's existing rule that no native control looks right in dark mode without help (`FlatProgressBar`/`ThemedMessageBox` exist for the same reason - see "Visual overhaul" below).
- **Remove button** (`Ctrl.DangerButton`) - confirms, then loads `BuildState`, removes just that `arch` key (dropping the outer `buildNum` entry too if it was the last arch), saves, and reopens the window. Does not touch any files on disk - matches `ClearState`'s existing "will NOT delete any downloaded files" framing. Since `Fetcher.Run`'s skip check is `buildState.ContainsKey(baseNum) && buildState[baseNum].ContainsKey(arch)`, removing the entry alone is sufficient to make the next scan (manual or monitor-mode automatic) treat it as incomplete and reprocess it - `Processor.ProcessBuild` has no "already done" short-circuit of its own, so this really does force a full extract/patch/capture redo, and `Net.DownloadFile` already skips re-downloading any raw file still on disk whose checksum still matches, so only genuinely-missing/corrupt raw files get re-fetched.
- **Upload button** - only enabled when `AppConfig.UploadDest` is non-empty (shown disabled as "Upload (no dest)" otherwise, rather than hidden - matches the existing style of surfacing the "no destination configured" state as a visible warning elsewhere in `MainForm`, e.g. the startup `QueueLog` warning, rather than silently omitting UI). Required extracting the upload/cleanup tail of `Processor.ProcessBuild` into a new standalone `Processor.UploadBuild(buildDir, uploadDest, cleanup, log, stopEvent)` (`ProcessBuild` now just calls it once at the end) so this button can re-trigger only the transfer for an already-processed build without redoing extraction/patching/capture - it re-derives `arch`/`buildVer`/`outputFolder` from `buildDir` the same way `ProcessBuild` does, and no-ops (logged) if `outputFolder` doesn't exist. Runs on its own background `Thread` (disables the button, `Thread`, `win.BeginInvoke` back to re-enable it when done) since copying a multi-GB ESD to a network destination can take a while and must not freeze the dialog; **deliberately always passes `cleanup: false`** regardless of `AppConfig.CleanupAfterUpload` - a manual "upload this again" click should never silently delete the local build folder as a side effect, unlike the automatic post-processing path where cleanup is an intentional, configured behavior.
- **File list is a real grid** (`Name`/`MD5`/`SHA256` columns via `TableLayoutPanel` with `CellBorderStyle.Single`, built by the small `MainForm.MakeGridCell` helper) - was one overflowing monospace line per file before (visible in a real screenshot the user attached: the sha256 ran off the edge of the row). Column widths (`colName=280, colMd5=230, colSha=460`) were sized against real text metrics, not guessed - a standalone `Graphics.MeasureString` harness measured Consolas 8pt needs ~390px for a full 64-char sha256 and ~197px for a 32-char md5, so 460/230 leave real margin rather than just barely fitting. `row.Width` bumped to 1000 and the window's default/minimum size widened to match.
- **Actually visually verified**, not just compiled: no native-Win32 GUI automation tool is available in this environment (only browser automation), so a standalone harness invoked `MainForm.ShowState()` via reflection against a seeded scratch `builds.json` (isolated download dir via `Paths.SetDownloadDir`, never touching the user's real one), used a `System.Windows.Forms.Timer` to grab a `Control.DrawToBitmap` screenshot of the live modal dialog, then closed it - the resulting PNG was read directly and confirmed the grid renders correctly with full untruncated hashes. Same technique (`DrawToBitmap` + a timer that finds and closes the dialog by `Form.Text`) is reusable for verifying any future WinForms change in this project the same way, given no dedicated native GUI automation tool exists here.

## Download list trimmed to only what Processor needs - `Fetcher.TrimUnneededFiles`
Confirmed by the user via a real "Downloaded Builds" screenshot and direct observation: the direct-from-Microsoft path (`WuClient`) does not exclude the old checkpoint MSU the way the original uupdump.net-scrape-based implementation did (that old filter hardcoded a skip for `KB5043080` by name, automatic-scan-only - see the untouched scrape-fallback filter in `Fetcher.Run`, still there for its own code path), and also offers extra files direct discovery doesn't need at all: `*.AggregatedMetadata.cab`, `DesktopDeployment.cab`, and a second/older `.msu` or extra cabs. Lives in its own method, `internal static List<UupFile> Fetcher.TrimUnneededFiles(string baseNum, List<UupFile> filtered, Action<string> log)` - `internal` specifically so a standalone test harness compiled into the same assembly can call it directly against real captured file lists (see the "real regression" note below for why that mattered). Called from `Fetcher.Run` right after the NDP-fallback-sibling gate (so it sees whichever build's file list actually won, original or a sibling substitution) and before `targetDir`/download.
- **22621/22631 (22H2/23H2, normalized to baseNum `22621.x`)** is the one family that ships differently - no `.msu` wrapper at all (confirmed in the "why it's safe to remove [7z] outright" section above: standalone `.wim`/`.psf`/SSU cab), so there's no "biggest .msu" concept here. Keeps exactly the four kinds of file `Processor.ProcessBuild`'s own `FindFirst` calls ever look for - `*.wim`, `*.psf`, anything with "SSU" in the name, anything with "NDP" in the name - drops everything else (in practice `AggregatedMetadata.cab`, `DesktopDeployment.cab`, and any other extra KB cab Microsoft bundles in - both families are past `FilterUpdateOnly`'s `build > 21380` threshold that adds the first two back in unconditionally, whether needed or not).
- **Every other branch** (24H2/25H2/26H2/26H1, and any future branch by default rather than needing its own whitelist entry each time Microsoft ships a new one) gets the "biggest `.msu` + NDP only" trim: the combined SSU+LCU "checkpoint" `.msu` already bundles the WIM/PSF/SSU cab Processor needs internally (per the "combined SSU+LCU checkpoint" notes above), so only the single **largest** `.msu` by byte size (not by KB number - generalizes across whichever KB happens to be the real payload this time, unlike the old hardcoded-`KB5043080` approach) plus the separate NDP cab are needed. Confirmed 26H1 (28000) needed this too via a real scan's log, not just 26100 - it was downloading all 6 offered files instead of the 2 actually needed, which is what prompted generalizing the condition from an explicit `baseNum.StartsWith("26100")` allow-list to an `if (22621-family) {...} else {...}` default, so any branch not explicitly known to ship differently gets this trim automatically.
- Added a `Size` field to `UupFile` (Fetcher.cs), populated from `WuClient.FileEntry.Size` (already parsed from the real `<File Size="...">` attribute, no new protocol call needed) in `WuClient.ResolveUpdateOnlyFiles`. Left at 0 for files resolved via the uupdump.net `get.php` scrape fallback (`HtmlParser.ParseGetPage` - its aria2-format response has no size field at all), so the "biggest .msu" comparison degrades to "first .msu in list order" there - acceptable since that fallback path's own pre-existing `KB5043080`-name filter already normally leaves at most one `.msu` by the time this trim runs.

**Real regression, found by checking a real scan's log rather than trusting the earlier "it compiles" verification**: the first version of this (added the 22621 case as an `else if` right after the 26100 case's `if` block) actually welded the new `else if (baseNum.StartsWith("22621"))` onto the **wrong** preceding `if` - an `Edit` call's `old_string` match spanned from a comment back through the entire original `if (baseNum.StartsWith("26100")) {...}` block, and the replacement text deleted that whole `if` while keeping only the new `else if`, which then silently reattached itself to the NDP-fallback gate's `if (!isManualBuild) {...}` several lines above. Net effect: the 22621 trim could only ever execute when `isManualBuild` was true (manual build-number entry) - never during an automatic scan, since `!isManualBuild` is always true there and an `if`/`else if` chain only ever runs one branch - and the entire 26100 "biggest .msu" block was gone outright, no branch ran it at all any more. Caught by checking `uupdump.log` after a real automatic 23H2 scan and seeing all 9 raw files still being downloaded with no "Trimmed to..." log line anywhere for that run (`grep -c "Trimmed to"` across the whole log only ever found the two hits from *before* this regression was introduced). **Lesson: an `Edit` whose `old_string` happens to span from one `if` block's leading comment through to include a whole unrelated following code region can silently delete that region instead of the caller's intended one** - after any such edit that touches control-flow structure (if/else chains especially), re-read the surrounding code to confirm the brace/keyword structure still says what it's supposed to, don't just trust that the compiler accepting it means the logic is still right.
Fixed by extracting the whole trim into `TrimUnneededFiles` as its own standalone method (no longer inline in the middle of an unrelated if/else chain, so this class of accidental-attachment bug can't recur the same way) and verified two ways: unit-tested directly against three real captured file lists (23H2's real 9-file list, 26H2's real 7-file list with real sizes, 26H1's real 6-file list from the log that first showed the bug) via a standalone harness calling `Fetcher.TrimUnneededFiles` - all three now trim to exactly the expected files; and confirmed a clean rebuild picks it up (had to ask the user before stopping their own running `uupdump.exe` process first, since it held a lock on the output exe - don't assume it's safe to kill a user's running instance of their own tool without asking, even if its log looks idle).

## Assembly version auto-increments every build (starts at 2.0.0.0)

## uupdump.net dependency (direct-first, uupdump.net kept as fallback)
`Fetcher` now tries Microsoft's own Windows Update servers directly first (via `WuClient`), and only falls back to scraping uupdump.net when the direct path fails - the user explicitly asked to keep uupdump.net as a failsafe rather than remove it outright. Both paths produce the same `BuildInfo`/`UupFile` shapes so the rest of `Fetcher.Run` (branch/arch dedup, `BuildState` tracking, download loop, `Processor` handoff) doesn't care which one served a given build.

- **Discovery** (`known.php` equivalent): `WuClient.DiscoverLatest`/`DiscoverExact` call Microsoft's `SyncUpdates` SOAP endpoint directly. `Fetcher.Categories` now carries a seed build number per branch category (used only as a baseline/branch-codename hint - Microsoft returns whatever is actually current for that branch). Per category, `Fetcher.Run` tries `WuClient` for each requested arch and only falls back to `known.php` (scraping uupdump.net) for archs it couldn't resolve directly - same shape for the manual-build-number path, using the `'thisonly'` SOAP flag to ask Microsoft for that exact build.
- **File resolution** (`get.php` equivalent): `WuClient.ResolveUpdateOnlyFiles` calls `GetExtendedUpdateInfo2` directly and applies a faithful C# port of `get.php`'s own `edition=updateOnly` filter chain (diffs/baseless/express-cab/psf dedup, then the KB/SSU regex + `AggregatedMetadata`/`DesktopDeployment` for build > 21380 - see `WuClient.FilterUpdateOnly`). Returns `null` on any failure so `Fetcher.Run` falls back to scraping uupdump.net's `get.php` (which then needs this tool's own simpler NDP481/SSU/KB5043080 filter, since the raw scrape isn't pre-filtered).
- **Per-file descriptions (what KB a given downloaded cab/msu actually is) are NOT recoverable from this protocol path - verified live, don't re-attempt without new evidence.** Tried adding a `Title`/`Description` field threaded from `ParseSyncUpdates`' per-fragment `<Title>` node through `FileEntry`/`UupFile`, on the theory that each bundled KB (LCU/SSU/NDP481/etc.) arrives as its own `<Update>` XML fragment with its own `<Title>`, sharing only the local numeric `<ID>`. Live-tested against a real 23H2 build via a standalone harness (same pattern as other verified sections of this doc: compiled the real project sources plus a throwaway `Main` via `/main:`, with `ServicePointManager.SecurityProtocol`/`ServerCertificateValidationCallback` copied from `Program.Main` in Core.cs since a harness that skips that entry point fails the Microsoft TLS handshake): a real `'thisonly'` `SyncUpdates` response for that build returned exactly ONE `IsLeaf=true`/`ProductReleaseInstalled` entry (the main OS product - no separate leaf for NDP/SSU/companion products despite them being in the request's product list) and only 4 distinct `<Title>` values in the entire 5.4 MB response (`Windows 11, version 23H2`, `Global Secure Access`, `Windows`, `Windows Subsystem for Linux`) - generic component-classification labels, not per-KB. All 9 real downloaded files (LCU/SSU/NDP481/PSF/WIM/AggregatedMetadata/etc.) came back with no usable per-file title at all. Individual `<File>` elements themselves only carry `FileName`/`Digest`/`DigestAlgorithm`/`Size`/`Modified`/`PatchingType` attributes - no description-like attribute either. The change was fully reverted after this was confirmed. Filename pattern matching (SSU-*/NDP481/KB regex, already used throughout `Fetcher.cs`/`WuClient.cs`) remains the only way this tool identifies what a given file is.
- Ring selection is auto-probed (`WuClient.RingProbeOrder = RETAIL, WIF, WIS, RP`) since which channel currently serves a given branch shifts over time as Microsoft ships.
- **`Fetcher.Run` gates whole builds on NDP presence, automatic scans only**: after `filtered` is computed (either path), if none of its filenames contain "NDP" the tool retries before giving up (see `NdpFallbackBuildNums` below); if nothing recovers it, the entire build is skipped (`continue`, logged) rather than downloaded without it - mirrors the pre-existing per-file NDP481/SSU keep-list, but rejects the build outright instead of just dropping one file. Same `isManualBuild` bypass as the KB5043080 exclusion: an explicitly requested build number is never skipped for this. `Processor.cs`'s own NDP handling (`FindFirst(buildDir, "*NDP*.cab")`) was already optional/non-fatal before this change and is unaffected - the new gate runs earlier, before anything is downloaded.
- **NDP presence genuinely differs across "sibling views" of the same base build, confirmed live by the user against uupdump.net's `known.php?q=<suffix>+<arch>`** (e.g. suffix `9278`): the 26H2 view (26300.x) can omit the NDP cab from its file manifest while the 24H2 (26100.x) and 25H2 (26200.x) views of the exact same base build include it - these are separately-resolvable Microsoft update objects (distinct UpdateIDs/revisions, per the "Branch category note" above), each with its own bundled companion-file list, even though the underlying LCU/SSU/PSF payload is the same across all members. Since 24H2 has no Settings tick box and 25H2 has no live category at all (both manual-search-only per `Categories`), an automatic scan that only checks 26H2 would previously just skip a build like this outright. Fixed: when the primary view lacks NDP, `Fetcher.Run`'s gate now calls `NdpFallbackBuildNums(buildNum)` to get the other members of buildNum's family from `NdpSiblingFamilies` (same trailing build suffix, family order = fallback-preference order), re-resolves each via a fresh `WuClient.DiscoverExact`+`ResolveUpdateOnlyFiles`, and substitutes the first one whose manifest does contain NDP for `files`/`filtered` - keeping the *original* `b.Branch`/`baseNum` (computed earlier, before this gate runs) so the recovered content still lands in the intended branch's folder rather than a different one. Two families defined: `26300/26200/26100` (26H2/25H2/24H2) and `22631/22621` (23H2/22H2, added on request without independent live confirmation that 22H2/23H2 actually diverge on NDP the same way - same mechanism, applied by analogy). Not yet live-tested end-to-end for either family (no live NDP-missing build available at edit time to confirm the substitution downloads and processes correctly) - if a future scan hits this path and something looks wrong, check here first.

**uupdump.net's backend is itself open source** at `git.uupdump.net/uup-dump` (Gitea instance; WebFetch on it returns an AI-summarized page, not verbatim source - use `curl -sL <url>/raw/branch/master/<path>` instead, which returns real file content). Repos: `api` (the live PHP backend - `WuClient.cs` is a from-scratch C# port of `fetchupd.php`/`get.php`/`shared/{auths,requests,utils}.php`, verified line-by-line against the real PHP and then against live Microsoft responses, not guessed), `standalone`, `converter` (not needed for the ESD-assembly part - `Processor`/`PsfPatcher` already does UUP->ESD assembly locally; note this produces the compressed WIM-format servicing image only, not a bootable ISO - no boot files/WinPE step exists in this tool), `json-api`, `contrib`, `misc`, `lightuup`.

Protocol (verified live against Microsoft during this session, see below):
1. **GetCookie** SOAP call to `https://fe3.delivery.mp.microsoft.com/ClientWebService/client.asmx` returns an `EncryptedData` cookie blob (`WuClient.GetEncryptedCookie`, cached ~20h in memory, real server-side validity is much longer).
2. **SyncUpdates** SOAP call to the same endpoint with a `DeviceAttributes` blob and a `Products` list (`PN=Client.OS.rs2.<arch>&Branch=<branch>&V=10.0.<build>.<minor>&...` plus Edge/NETFX/Appraiser/OOBE/etc companion products - Microsoft can return multiple simultaneous leaf updates across those companion products in one response, so `WuClient.ParseSyncUpdates` explicitly filters to the leaf whose `ProductReleaseInstalled Name` matches `Client.OS.rs2.<arch>` exactly, rather than blindly taking the first leaf like the PHP does). Response XML embeds child structure as HTML-entity-escaped text inside `<Xml>` elements (e.g. `<UpdateInfo><Xml>&lt;UpdateIdentity .../&gt;...</Xml></UpdateInfo>`) - `WuClient` parses the well-formed outer document with `XmlDocument`/`XmlNamespaceManager` (namespace `http://www.microsoft.com/SoftwareDistribution/Server/ClientWebService`) and then re-parses each `<Xml>` element's already-unescaped `.InnerText` as its own fragment, rather than the PHP's flatten-the-whole-document-then-regex approach. Per-file metadata (name/SHA1/SHA256/size) and the localized title live in *separate* `<Update>` entries under `ExtendedUpdateInfo/Updates` that share the same local numeric `<ID>` as the `<UpdateInfo>` leaf (not the UpdateIdentity GUID) - join on that.
3. **GetExtendedUpdateInfo2** SOAP call to `https://fe3cr.delivery.mp.microsoft.com/ClientWebService/client.asmx/secured` for a specific `UpdateID`/`RevisionNumber` - no cookie needed for this call (unlike SyncUpdates) - returns real Microsoft CDN file URLs (`FileLocations/FileLocation/Url` + `FileDigest` SHA1), matched back to names/SHA256 by SHA1. `WuClient.ResolveUpdateOnlyFiles` re-runs a `'thisonly'` SyncUpdates call to get that name/hash metadata rather than threading the original discovery result through, so it stays usable standalone against a build discovered via the legacy uupdump.net scrape too.
4. Live-verified surprise: a current Windows 11 24H2/25H2 `updateOnly` fetch now includes a ~0.9-4.6 GB "combined SSU+LCU checkpoint" MSU (Microsoft's periodic full-checkpoint servicing model, WIM-formatted) alongside the normal small delta cab - this is genuinely what `edition=updateOnly` resolves to now, not a bug in the filter. See "wimlib: DLL-direct" above - this checkpoint format now processes end-to-end successfully. 23H2 is still the cheapest build for a quick smoke test (~1 GB total, plain SSU cab + WIM + PSF, no checkpoint), but 24H2+/25H2 is no longer expected to fail.
5. Old-build reachability is better than expected: the `'thisonly'` flag successfully pulled the 24H2 RTM (build 26100.1742, over a year old at test time) directly from Microsoft. The known limitation (Microsoft eventually ages very old builds off live serving, where uupdump.net's own historical database would still have them) is real but narrower than assumed going in - the uupdump.net fallback exists for whatever this direct path still can't reach, per user's explicit "leave uupdump.net as failsafe" instruction.

## 7z: removed entirely - CAB fallback is now CabinetApi (cabinet.dll, no embedded binary)
`7z.exe`/`7z.dll` are gone from `assets\`, `build.cmd`, and `Paths` (`Paths.SevenZip` removed). `ToolHelper.ExtractMsu`'s classic-CAB fallback (used when `WimLibApi.TryExtractAsWim` reports `WIMLIB_ERR_NOT_A_WIM_FILE`) calls `CabinetApi.ExtractCab` with no further fallback - a direct P/Invoke binding to the OS's own `cabinet.dll` (the FDI - File Decompression Interface - API `expand.exe`/Explorer's own CAB handler use internally). Confirmed present and exporting `FDICreate`/`FDICopy`/`FDIDestroy`/`FDIIsCabinet` via `GetProcAddress` against the real `C:\Windows\System32\cabinet.dll` on this machine (file version 5.00) - unlike `libwim-15.dll` this needs **no embedded binary and no `LoadLibrary`-by-full-path dance**, a bare `DllImport("cabinet.dll")` resolves it off the System32 search path.
- **Why it's safe to remove outright, not just deprioritize**: every branch this tool currently handles resolves through `WimLibApi`, never classic CAB - 23H2 ships its LCU as standalone `.wim`/`.psf` files directly (no `.msu`/`.cab` wrapper at all, confirmed by inspecting a real downloaded 23H2 build folder), and 24H2/26H2/26H1 all share the WIM-formatted-checkpoint build-number range (26100+/26300+/28000+, per `Fetcher.Categories`' seed builds - well past the 25336 WIM-checkpoint threshold). `ToolHelper.Run7z`/`MakeHidden`/`ToolHelper.ActiveProcess`/`ToolHelper.KillActive` (all 7z-subprocess-only machinery) were deleted from `Processor.cs`; `MainForm.OnStop` no longer calls `KillActive()` - Stop is now purely cooperative (`_stopEvent.Set()`, polled by `WimLibApi`/`CabinetApi`'s own progress callbacks), since there's no child process left to kill. Also deleted from `assets\`: `wimlib-imagex.exe` (already unused, confirmed no reference anywhere) and `7z.dll` (only ever referenced by `SevenZipApi.cs`, never embedded).
- Every signature/struct/flag/constant in `CabinetApi.cs` was verified against real sources, not guessed: FDICreate/FDICopy/FDIDestroy prototypes and the FNALLOC/FNFREE/FNOPEN/FNREAD/FNWRITE/FNCLOSE/FNSEEK/PFNFDINOTIFY macro expansions from mingw-w64's real `fdi.h`; the FDINOTIFICATION/ERF struct layout, FDINOTIFICATIONTYPE values, and the exact per-notification return-value contract (0/-1/handle for `fdintCOPY_FILE`; TRUE/FALSE/-1 for `fdintCLOSE_FILE_INFO`, and the fact that FDI never calls `PFNCLOSE` itself for that handle - the app must close it from inside that callback) from Microsoft's own Learn docs; `_O_*`/`_S_I*` flag values from mingw-w64's `fcntl.h`/`sys/stat.h`; `_A_RDONLY`/`_A_HIDDEN`/`_A_SYSTEM`/`_A_EXEC`/`_A_NAME_IS_UTF` cabinet attribute bits from the Cabinet Format spec.
- **DIAMONDAPI is `__cdecl`**, for every FDI entry point and every callback - declared correctly per the header even though this project's x64-only target (`/platform:x64`) makes the calling-convention attribute practically harmless (one uniform convention on x64), same reasoning as `WimLibApi.cs`'s own note.
- **Long-path safety bit us twice here too, same underlying cause as the WIM side**: a real SSU/servicing-stack cab's internal files sit under WinSxS-style component names 100+ chars long. First bug: destination file creation/opening used plain `System.IO`/`Path.GetFullPath` - fixed by routing every destination create/open/mkdir through `LongIO` (defined in `Processor.cs`, same namespace) and building destination paths with plain string concatenation, never `Path.Combine`/`Path.GetFullPath`. **Second, sneakier bug found only via live testing**: even `Path.GetDirectoryName` - believed to be pure string manipulation with no filesystem/length validation - actually calls `Path.InternalGetDirectoryName` → `Path.LegacyNormalizePath` internally in .NET 4.8, and threw `PathTooLongException` on the exact same deep names `LongIO` was already routing everything else around. Fixed by replacing it with manual `LastIndexOf('\\')`/`Substring` splitting for any path that might be deep. **Lesson: don't assume any `System.IO.Path.*` method is exempt from the framework's own path-length validation just because it looks like pure string manipulation - `GetFullPath` obviously validates, but so does `GetDirectoryName`.**
- **Verified byte-for-byte against the real 7z.exe before it was removed**, offline: extracted a genuine downloaded `SSU-22621.6120-x64.cab` (a real WinSxS-deep SSU package, exactly the shape that surfaced both long-path bugs above) via a standalone console harness, and separately via 7z.exe. Identical file count (219/219), identical relative paths, identical sizes, and identical SHA256 on every file spot-checked including the largest (1.4 MB) - a CAB's content format doesn't care whether the source file is named `.cab` or `.msu`, so this is a complete functional proof of the same `FDICopy` code path `ExtractMsu` now calls for classic `.msu`s too.
- **Not yet live-GUI-exercised against a real classic-CAB-formatted `.msu`**, because no currently-live Microsoft-served Windows 11 branch needs one (see above) - the offline byte-for-byte test above is the real proof this path works. It's kept in `Processor.cs`/`build.cmd` anyway (unlike 7z.exe) because it costs nothing to keep: no embedded binary, no subprocess, just a P/Invoke against a DLL every Windows install already has. If a future build (an older Windows 10 patch level, or a format regression) needs classic CAB again, this is already wired in and ready.
- **`SevenZipApi.cs` was deleted** (a full direct-`7z.dll` COM-interop implementation from an earlier session, never referenced by `build.cmd`) - fully superseded by `CabinetApi.cs` for the CAB case, and with `7z.exe`/`7z.dll` gone entirely there was no reason left to keep it around. Worth remembering if 7z-direct P/Invoke is ever attempted again: it was blocked on `IInArchive.Open()` for **WIM** format returning `E_POINTER` (0x80004003) immediately after a successful 208-byte header read, and the same call also failed for **CAB** the instant it reached the extract callback. Every GUID/vtable order/PropVariant layout was independently verified correct against real `ip7z/7zip` source and `SevenZipSharp`, x64's single calling convention ruled out stdcall/cdecl stack-imbalance theories, and CHandler's multiple-COM-interface inheritance was traced through 7-Zip's own `MyCom.h` QueryInterface macros without finding a flaw - root cause was never found. `CabinetApi.cs`'s cabinet.dll/FDI approach avoided this whole class of problem by not going through 7-Zip's COM interface at all.

**Real bug found and fixed along the way, worth remembering for next time**: `WimLibApi.Capture`'s progress-callback delegate was being passed to `wimlib_register_progress_function` as a bare local variable with no reference afterward - the JIT considered it dead after that call, so it was eligible for GC while wimlib's compression threads still held and called the raw native function pointer during `wimlib_write`. This worked fine in a low-GC-pressure console test harness but threw an intermittent `NullReferenceException` under the real GUI's heavier allocation activity (reproduced twice via the real app before diagnosing it with an isolated repro). Fixed with `GC.KeepAlive(callback)` placed after the last native call that could invoke it. **Any future P/Invoke callback delegate in this codebase must do the same** - a delegate passed to native code needs an explicit `GC.KeepAlive()` (or an equivalent field-rooted lifetime) covering every native call that might still invoke it, not just "stays in scope as a local."
